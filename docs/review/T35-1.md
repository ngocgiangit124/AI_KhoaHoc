### Tổng quan
Bản dựng chắc tay: `set -euo pipefail`, trap trả `log_bin_trust_function_creators` về 0, khoá bằng `mkdir`, không có `compose down`, quyền 0600 cho env và backup, hardening compose tốt (cap_drop ALL, no-new-privileges, worker-video read_only và mạng internal, MySQL/Redis không publish), healthcheck admin đã đúng `/dang-nhap`, preflight guard cho cả app lẫn worker trước khi đổi gì. Có một lỗi logic ở đường khôi phục (R1) cần sửa trước khi duyệt, vì đây là đúng tình huống mà rollback phải hoạt động.

### R1 [BLOCKER] Deploy lỗi sau khi đổi container (smoke-failed / swap-failed) để `.env` ở tag cũ, `rollback` sau đó về SAI phiên bản
- Vị trí: `infra/production/deploy.sh` `do_deploy` (khối `dc up -d --no-deps --wait`, khối `run_smoke`, và `set_env_value` ở cuối, dòng ~377-407), `do_rollback` (dòng ~415), `print_recovery`.
- Vấn đề: `IMAGE_TAG`/`PREVIOUS_TAG` trong `$VV_HOME/.env` chỉ được ghi SAU smoke và recreate worker. Khi smoke lỗi (hoặc `up --wait` lỗi), container mới đang chạy nhưng `.env` vẫn `IMAGE_TAG=<cũ>` và `PREVIOUS_TAG=<cũ hơn>`. `print_recovery` in "rollback  # về tag <cũ>", nhưng `do_rollback` đọc `prev=PREVIOUS_TAG` nên đưa hệ thống về bản TRƯỚC bản cũ (hoặc `die "PREVIOUS_TAG trống"` nếu là deploy thứ hai). Đây là đúng kịch bản "release mới hỏng, quay lại" nên rất nguy hiểm: về nhầm bản có thể thiếu cột/migration đã áp. Hệ quả phụ: mọi `docker compose up` tay hoặc `status` sau đó dùng tag lệch với thứ đang chạy; `prune_old_images` không thấy lệch nhưng cũng có thể xoá nhầm. Smoke của Dev không có ca "deploy rồi smoke lỗi rồi rollback" (chỉ có `dev4` migrate lỗi, vốn chưa đổi container, nên không lộ).
- Đề xuất: ghi tag ngay trước khi đổi container (trạng thái "đã cam kết"), để `.env` luôn phản ánh thứ đang chạy:
  ~~~bash
  # trước "đổi container":
  if [[ "$old_tag" != "$SHA" ]]; then set_env_value PREVIOUS_TAG "$old_tag"; fi
  set_env_value IMAGE_TAG "$SHA"
  # ... up --wait, smoke ... (lỗi: print_recovery, rollback đọc đúng PREVIOUS_TAG = old_tag)
  ~~~
  Hoặc cho `rollback [<tag>]` nhận tag tường minh và `print_recovery` in đúng lệnh. Thêm biến thể smoke: deploy bản "smoke lỗi" (vd. `/up` 503 hoặc migrate đã áp nhưng route hỏng) rồi `rollback` phải về đúng bản cũ.

### R2 [SHOULD] `comm` chạy theo locale của máy, input lại sắp xếp theo `LC_ALL=C`
- Vị trí: `deploy.sh` `pending_migrations`, `unknown_migrations`, và `comm -12` trong `do_deploy`.
- Vấn đề: `sort` dùng `LC_ALL=C` nhưng `comm` không; trên Ubuntu với `en_US.UTF-8`/`C.UTF-8` thứ tự collation khác (bỏ qua `_`), `comm` có thể in "not in sorted order" lên stderr và cho kết quả sai (báo thừa/thiếu migration chờ, hay lọt migration `VV-IRREVERSIBLE`). Dev chạy smoke trên macOS/BSD nên không thấy.
- Đề xuất: đặt `export LC_ALL=C` đầu script (đơn giản nhất), hoặc `LC_ALL=C comm ...` ở cả 3 chỗ.

### R3 [SHOULD] Hai env file `redis.env`/`redis-video.env` (REDISCLI_AUTH): nên thay bằng user healthcheck không chứa secret
- Vị trí: `docker-compose.yml` service `redis`, `redis-video`; `deploy.sh` `check_inputs`; `users.acl`, `users.video-instance.acl`.
- Vấn đề: `default` là user toàn quyền của app (`+@all ~* &*`). ACL chủ ý chỉ lưu băm SHA-256, nhưng nay mật khẩu GỐC của nó nằm thêm trong env của chính container Redis (`docker inspect`, `/proc/1/environ`), nhân bản ra thêm 2 file cần đồng bộ khi xoay mật khẩu (app.env, ACL băm, redis.env: lệch là healthcheck đỏ và `--wait` làm deploy dừng). Phương án "không xác thực, chấp nhận NOAUTH" thì lại không phát hiện trạng thái LOADING (AOF đang nạp), nên Dev chọn xác thực là có lý do; nhưng có phương án tốt hơn cả hai.
- Đề xuất: thêm vào mỗi file ACL một user chỉ được PING, không mang secret của app:
  ~~~
  user vv_healthcheck on nopass resetkeys resetchannels -@all +ping
  ~~~
  Healthcheck: `redis-cli --user vv_healthcheck --pass x --no-auth-warning ping | grep -q PONG` (với `nopass`, mọi mật khẩu được nhận; PING sau auth vẫn trả LOADING khi đang nạp). Bỏ hai env file, bớt 2 bước dựng server, `check-acl.sh` thêm 1 kiểm (user này không làm được gì khác). Nếu PO/DBA vẫn muốn giữ REDISCLI_AUTH: chấp nhận được, nhưng ghi rõ vào ADR §8.6 và README việc xoay mật khẩu phải sửa 3 chỗ. Điểm PO (3): đề xuất ưu tiên user `vv_healthcheck`.

### D2 [SHOULD] Sao lưu: dump an toàn, nhưng thiếu binlog ngoài server, thiếu khoá chung với deploy, thiếu thử khôi phục

Cần sửa:
1. **Khoá chung với deploy.** Cron `backup-db.sh daily` không giữ `.deploy.lock.d`; nếu trùng giờ deploy thì dump có thể cắt ngang migration DDL (bảng bị `ALTER` giữa chừng làm dump lỗi hoặc cho schema lẫn lộn). 2. **PITR bằng binlog ngoài server.** Thêm `backup-binlog.sh` (cron mỗi giờ, RPO ≤ 1 giờ), lưu bản sao nén kèm `VV_BACKUP_UPLOAD_CMD`. Binlog chỉ do uid 999 đọc được trong thư mục dữ liệu, nên đọc qua `docker exec`:

```bash
#!/usr/bin/env bash
# cron: 5 * * * *  vvdeploy  /opt/vitaminvui/backup-binlog.sh >> /var/log/vitaminvui-backup.log 2>&1
set -euo pipefail
umask 077
VV_HOME="${VV_HOME:-/opt/vitaminvui}"; DEST="${VV_BINLOG_DIR:-/srv/vitaminvui/backups/binlog}"; PROJECT="${VV_PROJECT:-vvstack}"
dc() { docker compose --project-name "$PROJECT" --project-directory "$VV_HOME" -f "$VV_HOME/docker-compose.yml" --env-file "$VV_HOME/.env" "$@"; }
mkdir -p "$DEST"
dc exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot -e "FLUSH BINARY LOGS"'
# Sau FLUSH, file cuối là file đang ghi (rỗng); mọi file trước đó đã đóng.
mapfile -t files < <(dc exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot -N -e "SHOW BINARY LOGS"' | awk '{print $1}' | head -n -1)
for f in "${files[@]}"; do
    [[ -e "$DEST/$f.gz" ]] && continue
    dc exec -T mysql cat "/var/lib/mysql/$f" | gzip -c > "$DEST/$f.gz.partial"
    gzip -t "$DEST/$f.gz.partial" && mv "$DEST/$f.gz.partial" "$DEST/$f.gz"
    [[ -n "${VV_BACKUP_UPLOAD_CMD:-}" ]] && $VV_BACKUP_UPLOAD_CMD "$DEST/$f.gz"
done
find "$DEST" -name 'binlog.*.gz' -mtime +"${VV_BINLOG_KEEP_DAYS:-14}" -delete
```
   Lưu ý: nếu dùng GPG như dump thì mã hoá cả binlog (binlog chứa toàn bộ dữ liệu ghi, gồm PII). Thời hạn giữ ngoài server của binlog phải **bằng hoặc dài hơn** thời hạn dump cũ nhất còn dùng (đề xuất 30 ngày cả hai), vì PITR bắt đầu từ dump + mọi binlog sau toạ độ của dump đó. Binlog trong container tự xoá sau 7 ngày (`binlog_expire_logs_seconds`) nên bản ngoài server là nguồn duy nhất cho các ngày cũ hơn.
3. **Quy trình PITR (viết vào README, chưa replay đầy đủ trong lần thử này):** (a) dựng MySQL 8.4 trống, chạy `grants.sql`; (b) nạp `*.sql.gz`; (c) đọc toạ độ ở dòng `CHANGE REPLICATION SOURCE TO` trong dump; (d) `gunzip` các binlog từ file đó trở đi, rồi `mysqlbinlog --start-position=<pos> binlog.0000NN --stop-datetime='YYYY-MM-DD HH:MM:SS' binlog.0000NN+1 ... | mysql -uroot` (file đầu mới dùng `--start-position`; `--stop-datetime` theo múi giờ MySQL = UTC). Cần một lần diễn tập đầy đủ ở staging trước go-live.

Tối thiểu thủ công 1 lần/tháng và sau mỗi migration lớn.

### D3 [PASS] `log_bin_trust_function_creators` bật/tắt quanh migrate

Đã đo:
- Với `my.cnf` hiện tại (binlog bật), `vv_migrate` có `TRIGGER` mà `trust=0` → `CREATE TRIGGER` lỗi **1419**; `SET GLOBAL ...=1` bởi root → tạo được. Đúng như tài liệu.
- Các phương án thay thế **không dùng được/không nên**: `SET_USER_ID` đã bị gỡ khỏi 8.4 (lỗi cú pháp khi `GRANT`); `SET_ANY_DEFINER` KHÔNG vượt được 1419 (vẫn lỗi 1419); `GRANT SUPER` vượt được nhưng là quyền vĩnh viễn, rất rộng và đã deprecated ở 8.4 ⇒ tệ hơn nhiều so với cờ tạm. `SET sql_log_bin=0` loại DDL khỏi binlog, làm hỏng PITR. Vậy cơ chế hiện tại (bật tạm bằng root, `trap` trả về 0) là phương án đúng.

- `SET GLOBAL` không bền (không `PERSIST`): đã thử, sau `docker restart` giá trị về `0`. Vậy nếu `deploy.sh` bị SIGKILL, hoặc server khởi động lại, cờ không "dính" vĩnh viễn; `deploy.sh status` đã in giá trị.

### R17 [SHOULD] `rollback` kéo ảnh theo tag mà không qua cổng digest (S2 hở ở đường khẩn cấp)
- Vị trí: `infra/production/deploy.sh:561-565` (`do_rollback`), không gọi `require_digests`/`check_digests`/`verify_signatures`.
- Vấn đề: `.env` chỉ giữ `IMAGE_DIGEST_*` của bản MỚI. Rollback chạy `dc pull php ...` theo `PREVIOUS_TAG`, ghi đè ảnh cục bộ bằng bất cứ gì GHCR đang gắn với tag đó, không kiểm gì. Đúng loại tấn công (ghi đè tag `<sha>`) mà S2 muốn chặn, và rollback là lúc người vận hành ít để ý nhất. Ảnh bản cũ thường còn trên server (`prune_old_images` giữ 3 tag và không xoá `current`/`previous`).
- Đề xuất: không `pull` nếu ảnh đã có cục bộ; chỉ `pull` khi thiếu, và khi đó bắt buộc digest của tag đó (lấy từ `images-*.lock` cũ hoặc dòng `digest_backend=` trong `releases.log`) hoặc `--digest-file`:
  ~~~bash
  if docker image inspect "$(image_ref backend)" >/dev/null 2>&1; then
      log "ảnh $prev còn trên server, không pull (S2)"
  else
      require_digests   # thiếu thì dừng; người vận hành dán digest của bản cần quay về
      dc pull php $(worker_services) $(frontend_services) && check_digests
  fi
  ~~~
  Thêm một kiểm smoke: rollback không-local mà thiếu ảnh và thiếu digest phải dừng.
