# REVIEW: T26 (queue/scheduler) + throttle catalog SSR
**Kết luận:** APPROVE (0 Blocker, 0 Major, 6 Minor/NIT)
**Phạm vi:** working tree chưa commit, chỉ file T26/throttle catalog. Test: `pest -c phpunit.local-f.xml tests/Feature/T26 T11 T10 T01` = 152 passed.

## Tổng quan
Code gọn, đúng yêu cầu. `CatalogThrottle` an toàn: không có token đúng thì `X-Client-IP` bị bỏ qua hoàn toàn. Token so bằng `hash_equals` trên sha256 nên không lộ độ dài hay timing. Key có tiền tố `ssr-client:` nên không đụng bucket theo IP. Thứ tự limit đúng: limit per-IP kiểm tra trước, bị chặn thì không tính vào trần tổng. Lịch gom về một chỗ, không bị đăng ký đôi (VideoServiceProvider đã bỏ khối Schedule).

## Kiểm tra các điểm được yêu cầu soi
- **Giả mạo X-Client-IP không token:** không giả được. Token rỗng hoặc sai thì dùng `$request->ip()`. Token rỗng trong `.env` thì `isInternal` luôn false, kể cả khi client gửi header rỗng (có test).
- **Timing:** ổn.
- **Bucket chung:** SSR hợp lệ có 120/phút/IP khách và 6000/phút tổng. Tốt hơn trước (120/phút cho cả site). Xem M1, M2.
- **Timeout so với retry_after (90s):** OtpMail, StaffNewDeviceMail, EnrollmentDecisionMail = 30s. SyncVideoAssetStatusJob = 60s. Worker `--timeout=60`. Tất cả nhỏ hơn 90s. Không còn job nào khác dùng queue.
- **onOneServer:** cần cache có lock dùng chung. `.env.example` dùng `CACHE_STORE=redis`, còn mặc định trong code là `database`, cũng hỗ trợ lock. Chạy được. Local dùng 1 scheduler nên không ảnh hưởng.
- **otp:prune:** không xoá thứ còn cần. Limiter OTP đếm từ `otp_codes` trong cửa sổ tối đa 24h (OtpService:318-319). Giữ 7 ngày và chỉ xoá khi `expires_at < now`. Có index `created_at`. Xoá theo lô 1000 là đúng.
- **ops:health:** ngưỡng dùng `>` cho worker_age, scheduler_age, failed_jobs và backlog. `null` (chưa từng có nhịp) được tính là lỗi. Exit 1 khi có vấn đề.
- **Lịch videos:* của T11:** vẫn chạy với tần suất cũ (15 phút, mỗi giờ). Chỉ đổi `withoutOverlapping()` mặc định 24h thành 30 và 60 phút, kèm `onOneServer`. Xem M4.

## Phát hiện
### M1 [MINOR/Security-backlog] Token rỗng ở production âm thầm tắt tính năng
- Vị trí: `app/Support/ProductionConfigGuard.php` (`guardInternalToken`), `config/internal.php:15`
- Vấn đề: để trống là hợp lệ. Nếu quên cấu hình INTERNAL_API_TOKEN khi triển khai SSR, mọi người dùng lại dùng chung 1 bucket 120/phút theo IP server SSR. Đó là lỗi gốc mà task này sửa, và nó xảy ra mà không có cảnh báo nào.
- Đề xuất: ghi `Log::warning` lúc boot ở production khi token rỗng, hoặc thêm cờ `INTERNAL_API_REQUIRED=true` để guard bắt buộc có token.

### M2 [MINOR/Security-backlog] Trần tổng 6000/phút là điểm DoS chung
- Vị trí: `app/Support/CatalogThrottle.php:34`
- Vấn đề: botnet nhiều IP gọi qua SSR (SSR luôn gắn token) có thể làm đầy bucket `ssr-total`. Khi đó 429 xảy ra với mọi trang SSR của khách thật. Trước đây cũng chung bucket nên không tệ hơn, nhưng cần biết.
- Đề xuất: ghi nhận, xử lý ở WAF/CDN. Cân nhắc cho SSR retry hoặc fallback cache khi gặp 429.

### M3 [MINOR/Security-backlog] Nginx chưa xoá header nội bộ
- Vị trí: `infra/nginx/conf.d` và `snippets` (grep không thấy `X-Internal-Token` / `X-Client-IP`). `.env.example` nói "Nginx PHẢI xoá 2 header này" nhưng chưa có cấu hình thực tế.
- Vấn đề: hiện không khai thác được vì cần token đúng. Nhưng nếu token lộ hoặc header bị ghi đè sai chỗ thì không còn lớp phòng thủ nào khác.
- Đề xuất: ở server block công khai thêm `proxy_set_header X-Internal-Token ""; proxy_set_header X-Client-IP "";` (hoặc `fastcgi_param HTTP_X_INTERNAL_TOKEN "";`). Chỉ giữ lại ở listener nội bộ mà SSR gọi.

### M4 [MINOR] Heartbeat không chịu lỗi cache, và exports có thể báo động giả
- Vị trí: `app/Support/Heartbeat.php:13`, `app/Providers/OperationsServiceProvider.php` (Looping listener), `config/ops.php:8-9`
- Vấn đề:
  1. `Cache::put` trong listener `Looping` nằm ngoài try/catch của worker. Redis cache lỗi thì worker crash (restart: unless-stopped sẽ khởi động lại, nhưng tạo vòng crash).
  2. Comment config nói queue `exports` có timeout dài, nhưng `retry_after` là 90s và `worker_max_age` là 120s. Job exports dài hơn 90s sẽ bị phát lại và gây báo động giả "worker chết". Hiện chưa có job exports nên chưa lỗi.
  3. `withoutOverlapping(30/60)` rút ngắn thời hạn khoá so với 24h trước. `videos:prune-orphans` hoặc `counters:recount` chạy quá thời gian này có thể chạy chồng.
- Đề xuất:
  ~~~php
  public static function beat(string $name): void
  {
      try { Cache::put(config('ops.health.cache_prefix').$name, time(), 3600); }
      catch (\Throwable) { /* heartbeat không được làm sập worker */ }
  }
  ~~~
  Khi làm task exports: dùng connection riêng với `retry_after` lớn hơn timeout, và nâng `worker_max_age` tương ứng. Nên để expire `withoutOverlapping` lớn hơn thời gian chạy tối đa dự kiến.

### M5 [NIT] ops:health đếm failed_jobs bằng `count()` toàn bảng
- Vị trí: `app/Console/Commands/OpsHealthCommand.php:32`
- Vấn đề: bảng bị prune sau 720 giờ nên nhỏ, chấp nhận được. Chạy mỗi 5 phút, bảng lớn thì nên đếm có giới hạn.
- Đề xuất: bỏ qua nếu bảng nhỏ.

### M6 [NIT] Test chưa phủ một số nhánh

## Gợi ý cho QA
- Gửi `X-Client-IP` lạ kèm token sai và thiếu token: phải bị tính theo IP kết nối.
- Token đúng, 121 request từ cùng một client-ip: request thứ 121 phải 429, IP khác vẫn 200. Vượt 6000 tổng phải 429 cho mọi IP.
- `php artisan schedule:list`: đủ 8 lịch, không trùng `videos:*`.
- Tắt worker, sau 120s `ops:health` phải exit 1. Bật lại thì exit 0.
- Chạy `otp:prune --dry-run` rồi chạy thật. Gửi OTP lại ngay sau prune: bộ đếm 24h không bị lệch.
- Test boot production với token ngắn (<32) phải ném lỗi. Token rỗng thì chạy bình thường.
- Chạy 2 scheduler trên Redis dùng chung: mỗi lệnh chỉ chạy 1 lần.
