description: Recurring pattern to check when a Service method with a rate-limited HTTP entry point gets a second, unthrottled entry point later

When a domain Service method is protected ONLY by an HTTP-layer `throttle:<name>` middleware on its original route (not by an internal counter/check inside the Service itself), always check whether a LATER task adds a second route/caller that reaches the same Service method without going through that middleware.

**Why:** In the T04 (OTP) review (2026-09-28), `OtpService::send()` has zero internal rate limiting — it relies entirely on `throttle:otp-send` (cooldown 60s, 5/giờ, 10/ngày/user — api-contract §1.6, data-model §3.1 S9) being attached to the `POST /auth/otp/send` route. The same T04 diff adds `PUT /auth/contact` → `ContactService::update()` → `OtpService::sendIfChannelEnabled()` → `OtpService::send()`, but forgot to attach ANY throttle to the new route. Result: an authenticated student can spam real OTP emails to arbitrary (including victim) addresses by repeatedly toggling their own contact info, completely bypassing the security control that was the entire point of S9. This is the same *class* of bug as [[feedback-vitaminvui-review-findings]] (a security control that exists on one code path but not an equivalent second path) but at the application-Service layer instead of the package-route layer.

**How to apply:** Whenever a task adds a new caller of an existing Service method that has known abuse potential (OTP/email send, payment attempt, coupon check, login...), explicitly verify: (1) does the Service method itself enforce the limit, or does it trust the caller's middleware? (2) if it trusts the caller, does every route/caller reaching it have an equivalent `throttle:`? Prefer recommending the limit be moved/duplicated *inside* the Service (defense in depth) over just "add throttle to the new route", since a third future caller will make the same mistake otherwise.

Related, same review: adding a `Limit::response()` closure to a named `RateLimiter::for(...)` to hook a side-effect (e.g. writing an `audit_logs` row when a daily cap is hit) breaks this project's `ApiExceptionRenderer` — Laravel wraps the custom response in `Illuminate\Http\Exceptions\HttpResponseException`, which does NOT implement Symfony's `HttpExceptionInterface`, so `ApiExceptionRenderer::resolve()` (`backend/app/Support/ApiExceptionRenderer.php`) falls through to the generic `500 INTERNAL_ERROR` branch instead of preserving the intended `429`. Safe alternative: check `RateLimiter::tooManyAttempts()` explicitly inside the `RateLimiter::for()` closure (before returning the `Limit[]` array) and write the audit log there with a `Cache::add(...)` dedup guard, WITHOUT calling `->response()` on the `Limit` — leave the default 429 rendering alone.

**Update (2026-09-28, T04 round 2, commit `047bff2`):** Dev fixed both R1 (dual-layer: `throttle:otp-send` on `PUT /auth/contact` + `OtpService::assertUnderSendLimits()`/`assertCanSend()` counting real `otp_codes` rows in DB, called fail-closed *before* the contact-change transaction) and the audit-on-daily-limit suggestion (`AppServiceProvider::auditOnceIfDailyLimitReached()`, exactly the `RateLimiter::tooManyAttempts()` + `Cache::add` dedup pattern recommended above, reconstructing the internal `md5($limiterName.$rawKey)` cache key from `ThrottleRequests::$shouldHashKeys`). Confirmed via re-running `pint`/`phpstan`/`pest` independently (247 passed) and reading the diff line-by-line — both fixes are solid and covered by **real HTTP-level tests** (`ContactUpdateThrottleTest`, `OtpDailyLimitAuditTest`) that exercise the actual route/middleware stack, not mocks. This is the key lesson: when a fix hooks into Laravel internals (cache key hashing, `RateLimiter` behavior), insist the test go through the real HTTP route + real `ThrottleRequests` middleware — that test doubles as a regression guard against future Laravel upgrades changing that internal behavior silently. Residual: the DB-count-based `assertUnderSendLimits()` has a narrow TOCTOU race (count-then-insert, no lock) — accepted as NIT only because every current caller is also behind the atomic cache-based route throttle (layer 1); would need to be revisited if a future task calls `OtpService::send()` from an unthrottled route again.
